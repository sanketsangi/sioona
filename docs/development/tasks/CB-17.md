# CB-17 — Explicitly supervised external action

Date: 2026-10-16. Approver: Sanket. D10 authorizes local/sandbox implementation and verification, commit and push. Hosted migrations, deployment, production enablement and customer targets remain gated.

## Implementation

Based on `origin/main` at `620faf36a96c418dab5bd997c3f83318bf60e330`, above `032_live_ingest`. The pre-existing mixed implementation commit `b047b394` is preserved on `cb/CB-17-preserved-b047b394`; only the CB-17 paths were recovered, excluding unrelated site changes.

Migration `033_supervised_action_executions` is the single linear head. `action_proposals` versions extend the existing `supervised_action_decisions` authority through tenant-qualified foreign keys. Immutable proposals store canonical JSON and SHA-256. The execution outbox binds `(proposal_id, payload_sha256, target, actor_id, tenant_id, action_version, expires_at)`; database triggers prevent rebinding or reversing transitions. Approval lasts at most 15 minutes; the operator UI requests five minutes. A new proposal or draft re-decision supersedes the old proposal and invalidates its unattempted approval. Reviewers retain ordinary draft review; edits to a draft linked to an external proposal require a verified admin.

The separately approved operation is `intercom_internal_note`. The adapter fixes `type=admin` and `message_type=note`, numeric allowlisted conversation ID, fixed Intercom 2.14 reply endpoint, no attachments, no redirects and no transport retries. No customer-message mode exists. The exact approved payload is checked again immediately before dispatch, along with current active admin membership, expiry, sandbox allowlist and provider admin identity. Credentials are resolved from operator-owned tenant configuration, never from a request.

Always-enforced verified admin endpoints live under `/v1/tenants/{tenant_id}/external-actions`: list, propose, approve, execute and reconcile. They stay enforced in actor-auth off/shadow/enforce modes. The web proxy requires a signed admin session, canonical PostgreSQL mode and same-origin mutations; it uses the no-retry backend request helper. `/external-actions` presents payload, hash, version, target, approval expiry and persisted execution status. Approve Draft does not create any execution approval.

Each application transition appends a CB-18 `audit_events` row in the same database transaction. Proposal/execution IDs and action version reconstruct the private payload through persisted rows; audit metadata contains no note text, transcript, credential or provider response body. Failed results record `failed`; ambiguous results record `blocked`. Migration 033 extends CB-18's audit vocabulary and bounded version constraint. Action audit timestamps use actual insertion time rather than transaction-start time so concurrent lock waits do not invert the transition chronology.

Both new tables force tenant RLS, use the existing lifecycle write fence, and participate in tenant export, FK-safe deletion and restored-backup reconciliation. Retention excludes reviewed drafts with linked proposals to preserve execution history. Migration upgrade/downgrade shifts existing in-flight deletion checkpoints for the two prepended deletion steps; populated action/audit history blocks downgrade.

## Dispatch and recovery

`SIOONA_EXTERNAL_ACTIONS_ENABLED=0` remains the default. Execution also requires `SIOONA_EXTERNAL_ACTIONS_ENV=sandbox` and `SIOONA_EXTERNAL_ACTIONS_SANDBOX_CONFIG`, an operator-owned secret JSON map keyed by verified tenant ID. Each entry must include `sandbox:true`, a sandbox-only least-privilege token, numeric `admin_id`, and an exact array of permitted numeric `conversation_ids`. Invalid configuration fails closed. Provision only the Intercom conversation permissions required for internal notes; record the sandbox workspace/target and verify the token with the operator before any separately authorized live sandbox test. Never commit configuration values.

1. Review a persisted draft, then save a separate proposal with the sandbox target and internal note.
2. Inspect the complete payload, SHA-256, target and version. Approve that exact proposal with an expiry, then explicitly choose Post approved sandbox note and confirm.
3. The tenant lock serializes approvals, edits and dispatch. Commit `attempted` and its audit before making the provider request. Duplicate execution IDs never make another request. The Idempotency-Key header is defense in depth; correctness does not assume Intercom honors it.
4. A timeout, ambiguous HTTP result or malformed success receipt becomes `unknown`. A process crash leaves durable `attempted`; re-entry converts it to `unknown` without resubmitting. Replacement proposals for the same draft are blocked while any execution remains attempted/unknown.
5. A verified admin checks the sandbox conversation directly in Intercom and records succeeded/failed plus a bounded provider receipt or investigation reference through Reconcile. Reconciliation never sends a request. Verify absence before recording failed; an explicit new proposal and exact approval are required for any later dispatch. Never replay the original execution.
6. Turn the kill switch off to stop new attempts. It cannot undo an already submitted note. Preserve unknown receipts for investigation.

Provider contract: [Intercom 2.14 conversations API](https://developers.intercom.com/docs/references/2.14/rest-api/api.intercom.io/conversations). Release verification uses synthetic sandbox targets and mocked transport only; no real Intercom request or customer communication was performed.
