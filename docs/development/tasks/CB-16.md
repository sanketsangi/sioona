## Contract

- Intercom HMAC-SHA1 `X-Hub-Signature` over bounded exact raw bytes, using `INTERCOM_CLIENT_SECRET`. JSON is parsed only after constant-time verification. Signed `created_at` must be within `INTERCOM_REPLAY_WINDOW_SECONDS` (default 900, allowed 60–86400); future skew at most 60 seconds. This checks notification creation age, not an unsigned delivery timestamp.
- `INTERCOM_INSTALLATIONS_JSON` is a server-only workspace-to-installation/tenant registry. Example with synthetic values: `{"workspace1":{"tenantId":"tenant_partner","installationId":"install1"}}`. The persisted active installation must independently match the signed workspace. Reject both tenant-selector headers. No automatic installation from a webhook. Credentials stay in environment; database stores only the credential reference.
- `principal:live-ingest` alone accepts events. Verified admin membership is mandatory for installation, revocation, listing, recovery and checkpoints, including auth off/shadow modes.
- HTTP 202 means the event receipt (and, when ready, canonical input plus job) committed. Pending and dead-lettered receipts are accepted durably, not discarded. Persistence outages return content-free 503 with Retry-After. The productionized route never calls inline detection. The legacy polling and WhatsApp ingestion endpoints return 404.
- Event uniqueness is `(tenant, installation, provider event ID)`; a digest mismatch is an identity conflict. Same delivery returns its receipt. Complete conversation snapshots use tenant-scoped stable IDs and provider message/part IDs. Partial/unrecognized events retain provider source references in dead-letter state.
- A source watermark advances only when its canonical snapshot and job enqueue. Pending events dispatch in source-version order after earlier active jobs terminate. Older versions are recorded no-ops; equal-version different content is a recoverable conflict requiring a newer authoritative event. A deletion tombstone prevents future resurrection. Legal holds block source scrubbing into a dead letter.
- Source deletion cancels/fences related active jobs, scrubs canonical messages, evidence, display summaries, draft text, source snapshots and inbox payload copies, and invalidates derived tenant cache. Review/decision/financial records remain. Tenant deletion/export inventories include the new tables; forced RLS and persistent deletion fences apply.
- Existing worker budget, ledger, retry, lease and publication fences remain. No prompts/models changed. Jobs contain bounded references only. Unresolved events are not aged out; terminal event text expires after 180 days under manual retention, while replay receipts/tombstones remain.

## Operator flow (requires separate hosted approval)

1. Complete CB-03/CB-07 operational acceptance and signed CB-10 acceptance; provision/verify the worker separately. Apply migration `032_live_ingest` after `031_queue_search` before deploying the updated worker/API. Keep LIVE_INGEST unset until ready.
2. As a verified tenant admin, PUT `/v1/tenants/{tenant}/live/installations/{installation}` with `workspace_id`, `consent_reference` and `monitoring_reference` (bounded reference IDs, never customer prose). Set the matching server registry and app client secret through approved secret management. Record customer consent and a real monitoring owner/runbook; fixtures are not consent.
3. Confirm valid signed delivery persists before 202; invalid signatures, timestamp replay and forged tenant headers fail. Observe queue age, dead-letter counts, provider delivery failures and worker status through admin GET `/v1/tenants/{tenant}/live/events?after={cursor}&limit=50` (follow `next_cursor`). Endpoint responses contain bounded metadata, not event transcripts. Validate failure/recovery and revocation in staging before LIVE_INGEST=1.
4. For delivery gaps or partial payloads, fetch the identified conversation through Intercom's read API under operator control. Respect HTTP 429 Retry-After; retain the page cursor and retry the same page without checkpoint advance. Submit a full **redacted canonical snapshot**, preserving source/message IDs, through admin PUT `/live/installations/{installation}/events/{event}/resolution` for an unresolved receipt. For events that never reached Sioona, have Intercom redeliver or deliver a newly signed authoritative event. An old delivery outside the timestamp window requires deliberate provider reconciliation; never disable signature checks.
5. Advance the admin PUT `/live/installations/{installation}/checkpoint` only after all events for the source page have durable receipts, with `expected_cursor` and `cursor`. This is compare-and-set; recovery does not automatically fetch provider data or run a scheduler. Resolve a page before advancing it.
6. For a job dead letter after fixing its cause, explicitly POST `/live/installations/{installation}/events/{event}/requeue`. It preserves job/event identity, resets the bounded retry cycle and advances fencing. Revoked, superseded, missing-source, config-changed and equal-version-conflict jobs cannot be blindly restarted. Requeue emits an append-only audit receipt.
7. POST `/live/installations/{installation}/revoke` to stop intake and fence related jobs. Revocation is permanent for that installation ID. Provider credential revocation is a separate human action. No endpoint sends customer messages.
