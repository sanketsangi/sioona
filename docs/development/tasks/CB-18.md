## Behavior and boundaries

- Migration `029_audit_lifecycle` follows the inspected single head `028_batch_cache`. It adds audit, legal hold, deletion/tombstone, private export, and financial summary tables. It changes no model/prompt/provider routing and enables no scheduler.
- New lifecycle routes and the retired legacy wipe endpoint require a verified, current admin membership in **off, shadow and enforce** actor modes. Header role claims and service principals cannot substitute. Every route participates in tenant-isolation coverage.
- `audit_events` contains only the approved bounded columns, UUID actor/resource/correlation references, enum operations/results/reasons, and timestamps. Runtime gets INSERT/SELECT, no UPDATE/DELETE/TRUNCATE. No free-text audit input is accepted. Tenant/resource names and hold resource IDs are not copied into audit fields.
- Any active tenant or resource hold conservatively blocks the entire tenant's retention/deletion, protecting parent/derived copies. Admin read/export continues. Holds can be added between deletion batches; a completed tenant cannot acquire new holds. Released holds remain as bounded historical control records.
- Export uses a PostgreSQL REPEATABLE READ transaction, tenant predicates on every table, stable primary-key order, 250-row streaming, a versioned manifest and per-class SHA-256 checksums. The artifact is stored privately in Postgres, expires for access after 24 hours, and is revoked atomically at deletion confirmation. Each download rechecks current admin authority. No public URL/token, shared user row, signing key, credential, cache payload or operator-owned pilot request is exported.
- The local export envelope is capped at 25,000 rows / 16 MiB. An over-limit export fails atomically without a partial artifact. Retrying after interruption starts a new consistent snapshot; no snapshot transaction remains open across requests. Larger/multipart exports require a separately designed delivery path; no new storage service is provisioned.
- `wipe_tenant_data` owns the checkpointed deletion and explicit retention entry points. API clients must request deletion, type **`DELETE <exact tenant_id>`**, confirm, then explicitly advance bounded batches. Confirmation immediately cancels queued/leased jobs, increments lease tokens, revokes exports and commits a persistent write fence. PostgreSQL and SQLite reject late canonical inserts/updates. Existing in-flight provider calls cannot be recalled; their results cannot republish after the fence.
- Each deletion batch deletes at most 250 rows from its current table and atomically commits the count/checkpoint/audit. A failed batch rolls back before recording a bounded failure code; retry repeats only uncommitted work. Holds are rechecked at every boundary. Final evidence, caches, jobs, canonical rows, tenant controls, memberships and workspace are removed in FK order. Global inference controls and operator-owned `pilot_requests` remain.
- Preserve the currently executing admin until final workspace removal, so interruption does not remove resume authority. Shared user cleanup locks the user and checks **all** memberships via a narrow restricted definer function; RLS-hidden memberships cannot cause a shared user to be deleted. A user with zero memberships is removed. At completion membership authority is gone; save the final counts-only receipt returned by the final advance before leaving.
- Audit and financial totals remain for 365 days; counts-only deletion tombstones remain for restore reconciliation. Tombstones contain no source text. Financial totals distinguish unknown/pending attempts and do not convert missing cost into a claim of reconciled zero.
- `/lifecycle` provides policy, holds, private export, exact confirmation, progress/retry and receipt controls. `/economics` links to it. Web lifecycle operations require a signed admin session, canonical Postgres state mode and same-origin mutation requests. JSON demo resets are a separate corpus and cannot claim canonical lifecycle deletion. No lifecycle operation implicitly runs on navigation.

## Retention implementation

Manual/on-demand only. Each invocation uses a bounded batch per class; repeat to drain a backlog. UTC `created_at` is the default clock, `imported_at` for uploads, `updated_at` for mutable resume/settings/taxonomy, `reviewed_at`/`decided_at` for review records, `budget_day` for daily totals, and terminal job `updated_at` for jobs. Active jobs, pending attempts and unsettled reservations are not silently expired.

180-day expiry removes messages, evidence and detection output. Conversation identity fields, upload snapshots/source labels and prediction prose/value evidence are anonymized at 180 days while parent stubs preserve longer-lived review/outcome/FK history. Outcomes expire 365 days after `outcome_recorded_at`; feedback and supervised decisions expire after their review/decision clocks through the explicitly approved retention branch of `wipe_tenant_data`. FK-safe parent cleanup follows child expiry, retaining only anonymized parents needed by still-retained reviews/outcomes. Retryable failed jobs and active upload references are preserved. Settings/taxonomy expire at 365 days. Terminal jobs and their references expire after 30 days; cache entries have a 7-day maximum. Expired export access is denied immediately by time checks; physical bundle cleanup is manual. Audit/financial expiry is a narrow tenant- and age-restricted definer function, never a general audit delete grant. Legal holds take precedence.

The function-level inventory `DISPOSITIONS` is exhaustive and has a test requiring an explicit disposition for every registered table. No integration-secret store currently exists; adding one requires inventory/export allowlist/deletion/retention updates before use. JSON demo files, immutable bundled synthetic showcase packs, logs, provider copies, backups and external integration stores are outside canonical export; hosted inventory and execution remain separate gates.

## Backup expiry and restore reconciliation

Backups/PITR expire on the hosting provider's natural retention window. This implementation does **not** promise immediate backup deletion, mutate backups or claim a measured RPO/RTO.

Before a hosted restore: keep API reads and workers stopped; load the trusted, separately retained completed receipt inventory; bind each recorded tenant and invoke the operator-only `reconcile_tombstone` service primitive, then advance the existing deletion state machine until completed. The primitive revokes restored exports, re-fences restored work and restarts FK-safe checkpoints. A conflicting restored legal hold leaves the tenant fenced and blocked for human resolution. Do not expose the reconciliation primitive as an untrusted upload/API route. Verify zero displayable evidence, canonical/export/cache/job absence and shared-user preservation **before** restoring traffic. Receipt provenance and a real provider restore drill remain operator acceptance gates.
