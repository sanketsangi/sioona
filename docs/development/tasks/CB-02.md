## Review findings (severity → resolution)


### P1 — Server-side outbound attempts were invisible to the browser gate

Failing test first: `outbound-gate.test.mjs` introduced Node and Python negative controls that catch a denied connection and report `sent: false`. Both failed before the guarded runner existed. HTTP-handler controls additionally verify a successful local response cannot conceal an outbound attempt.

Resolution: `npm run e2e` starts the guarded runner. Node preload and Python startup guards deny non-loopback connections and append only a runtime marker to an isolated audit file; the runner fails on any marker after Playwright exits, regardless of application responses. Direct Playwright invocation without the runner is rejected. Browser interception remains unchanged.

CI additionally runs `guard-linux.sh`: IPv4/IPv6 OUTPUT rules attach only to a fresh process group ID, permit loopback, and reject other packets. The test command keeps the runner UID for workspace access but loses supplemental groups, capabilities, and privilege escalation. Denial counters fail the gate even when native libraries/subprocesses catch errors; rules and the temporary group are cleaned up. Linux-only negative controls run both HTTP handlers without runtime hooks to exercise this OS boundary. These controls are mandatory in the E2E job, not silently skipped there.

The isolated web server now uses `next build --webpack` / `next start`, with telemetry disabled and a synthetic identity key. The initial guarded development journey passed its UI assertions but the runner correctly failed on Next's npm-registry version check. Production mode avoids that development-only effect without exempting it from the guard. No product handler or pilot behavior changed.

Validation (2026-10-07): 11 local targeted regression tests passed, including Node/Python HTTP handlers returning `sent: false` while the runner fails. Linux firewall syntax checked with `bash -n`; actual firewall controls require Linux and have not run on this macOS host or GitHub Actions. Local runtime hooks are not claimed to sandbox arbitrary native code; the CI OS boundary covers that case.

### P2 — The canary directory exemption hid unrelated secrets

Failing test first: an actual staged Git scan with gitleaks 8.28.0 accepted a second synthetic key in `canary.txt` under the original directory exemption, causing the regression test to fail.

Resolution: the exemption now requires both the exact fixture path and exact synthetic secret (`condition = "AND"`, `regexTarget = "secret"`). Scanner tests prove the known fixture passes, while an extra secret in the same file, a sibling file, and the canary value at another path each fail. The scanner regression suite runs in the Gitleaks CI job.

A history scan exposed three copies of the same public canary introduced in commit `93f22b7` (two task-record mentions and one test assertion). Removed those literal duplicates from current docs/code and recorded only their exact historical fingerprints in `.gitleaksignore`. Owner: Sanket; disposition: intentional synthetic scanner fixture, not credentials. No path-wide or value-wide exemption was added for those copies.

Validation (2026-10-07): all four scanner tests passed with gitleaks 8.28.0; history scan covered 394 commits with zero unallowlisted findings. Final implementation validation is recorded below; the implementation SHA is at the top of this record.
